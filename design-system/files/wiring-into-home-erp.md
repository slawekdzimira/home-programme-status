# Wiring into Home ERP

Home ERP renders server-side: Jinja2 templates under `app/creditworks/web/templates`, Tailwind from the Play CDN (no build step), Alpine.js for behaviour, HTMX on a few pages. The system drops into that stack in two phases, and neither adds a build step.

- **Phase 1, the re-skin.** One stylesheet (`ds-reskin.css`), the Inter font and one attribute per shell. Every screen, flow, field and link stays exactly as it is; only colour, type, corners, fields, header and tables change. No template is edited.
- **Phase 2, the components.** Jinja macros (`ds/*.html`) replace hand-rolled markup page by page, when a page is touched for other work.

The clickable prototype (https://claude.ai/artifact/4UhozfM77uKQp7tBLTGDL4) is Phase 1 on today's screens. The ERP's real page templates are rendered through the ERP's own Jinja environment (`creditworks.web.templates`, with its filters, globals and the portal translation dict) at the versions the ERP locks (fastapi 0.137.1, starlette 1.3.1, jinja2 3.1.6), fed with fictional sample data, with `ds-reskin.css` over them. Its "New look" switch takes the stylesheet off to show the same page as it looks today.

## Phase 1: the re-skin

`ds-reskin.css` is generated by `reskin/build_reskin.py` from the ERP itself: it scans every template, Python module and static script for stock Tailwind colour classes (`bg-blue-600`, `text-gray-500`, `hover:bg-purple-700`, `focus:ring-indigo-500`, `from-teal-600`...), adds the class names templates assemble at runtime (`bg-{{ color }}-50`), and maps each one to the portal palette. Nothing else in the page is targeted, so the rules cannot move, hide or add anything.

| Stock family in the markup | Applicant | Landlord | Staff |
| --- | --- | --- | --- |
| `gray`, `slate`, `zinc`, `neutral`, `stone` | warm grey | lilac grey | cool grey |
| `blue`, `indigo`, `sky`, `cyan` | teal brand | violet brand | royal-blue action |
| `purple`, `violet`, `fuchsia` | violet tone | violet brand | violet tone |
| `teal` | teal brand | success green | success green |
| `green`, `emerald`, `lime` | success green | success green | success green |
| `red` | danger red | danger red | danger red (Figma staff red) |
| `yellow`, `amber`, `orange`, `pink`, `rose` | own warm tone | own warm tone | own warm tone |

On top of the colours it sets Inter, the system's corner radii, flat hairline edges in place of drop shadows, filled fields with a 10px corner, 600-weight filled buttons, a visible focus outline, the brand-dark table head with soft zebra rows, the gradient header band with rounded foot on applicant and landlord shells, and the navy top bar on staff pages.

To switch it on:

1. Copy `ds-reskin.css` to `web/static/css/` and the Inter woff2 files to `web/static/fonts/inter/`.
2. Link both after `main.css` in the shared heads: `components/applicant_flow_head.html`, `layouts/base.html` (line 24), `layouts/landlord.html` and `layouts/landlord_public.html` (the landlord sign-in extends it).
3. Put the portal on `<html>`: `data-portal="applicant"` in `layouts/applicant.html` and every standalone page that includes the flow head, `data-portal="landlord"` in the two landlord layouts, `data-portal="staff"` in `base.html`. Add `data-aa` to all of them for the accessible palette.
4. Rebuild the stylesheet (`python build_reskin.py`) whenever a release adds a colour class the scan has not seen. A unit test can pin that: every class `scan_classes()` finds in the templates has a rule in the file.

The re-skin rules carry the `:root[data-portal]` prefix, so they win over the Play CDN's utilities without `!important`, and a page without the attribute renders exactly as today. That also makes the rollback one attribute.

## Phase 2 files

| Put | Where | What |
| --- | --- | --- |
| `ds-reskin.css` | `web/static/css/` | Phase 1: the generated re-skin. Stays linked in Phase 2 for every page not yet moved onto the macros. |
| `ds-tokens.css` | `web/static/css/` | Every token as a CSS custom property, one block per theme. Generated from `tokens.json`; never edit by hand. |
| `ds.css` | `web/static/css/` | The component classes (`ds-*`): this system's `bundle.css` without its Google Fonts import. Plain CSS, no `@apply`. |
| `ds/*.html` | `web/templates/components/ds/` | Jinja macros: `actions.html`, `forms.html`, `status.html`, `navigation.html`, `content.html`, `overlay.html`. Each component card names its macro. |
| `ds/head.html`, `ds/tailwind_bridge.html` | `web/templates/components/ds/` | The three stylesheet links for a shell, and the script that maps tokens into the Tailwind config. |
| `ds/icons.html` | `web/templates/components/ds/` | `icon(name, cls)`: the 45 glyphs the components use, inlined SVG. |
| `language_switch.html` | `web/templates/components/` | The ERP's language switch redrawn as a `Segmented` (same macro, same arguments, plus `variant="band"`). It replaces the existing file, so `test_language_switch_macro.py` moves with it. |
| Inter | `web/static/fonts/inter/` | Self-hosted variable woff2 (latin, latin-ext) covering weights 400-700 with `font-display: swap`; the portal must not depend on a third-party font host. |

Type styles are classes named `ds-t-<style>` in `ds-tokens.css` (`ds-t-title-lg`, `ds-t-body`, `ds-t-small`...); on phones `ds.css` steps the title styles down to the Figma Mobile sizes.

## Link them in the shells

- **Applicant pages** (80 of them) share `components/applicant_flow_head.html`: link `ds-tokens.css` and `ds.css` there, before the Tailwind CDN `<script>`, and set `data-theme="resident-aa"` on `<html>` in `layouts/applicant.html` and every standalone page that includes the flow head.
- **Staff pages** (247) extend `layouts/base.html`: link both files at line 24 beside `main.css` and set `data-theme="staff-aa"`.
- Landlord shells (`layouts/landlord.html`, `landlord_public.html`): link the files and set `data-theme="landlord-aa"`. Agency (`layouts/agency.html`): `resident-aa`.
- The Play CDN appends its generated `<style>` at the end of `<head>`, so Tailwind utilities still win ties against `ds-*` classes. Use that for layout (`grid`, `gap-*`, `mt-*`), never to recolour a component.

## Bridge Tailwind to the tokens

Map the token names into the Tailwind config the flow head already declares, so legacy markup can move off the stock palette one class at a time:

```js
tailwind.config = { theme: { extend: {
  fontFamily: { sans: ['Inter', 'Helvetica Neue', 'Arial', 'system-ui', 'sans-serif'] },
  colors: {
    brand: 'var(--brand)', accent: 'var(--accent)', ink: 'var(--ink)',
    'ink-muted': 'var(--ink-muted)', 'ink-subtle': 'var(--ink-subtle)',
    page: 'var(--surface-page)', card: 'var(--surface-card)', field: 'var(--surface-field)',
    line: 'var(--border)', success: 'var(--success)', danger: 'var(--danger)'
  },
  borderRadius: { card: 'var(--radius-card)', panel: 'var(--radius-panel)', field: 'var(--radius-field)' }
} } };
```

Keep the applicant `fontSize` and `maxWidth` overrides in that file: its scale already lines up with the system (`text-xs` 14 = `small`, `text-sm` 16 = `body`, `text-base` 18 = `question`, `text-lg` 20 = `body-lg`, `text-xl` 22 = `lead`, `text-3xl` 32 = `title-md`), and a test pins `max-w-4xl` = 64rem.

## Order of work

0. **The re-skin (Phase 1 above).** The client sees the new look on every page at once; no screen or flow changes.
1. **Tokens, stylesheets, theme attributes.** Nothing changes on screen until a class is used; ship it alone.
2. **Shells.** `ResidentHeader` replaces the header in `layouts/applicant.html:16-69` and, through one include, the ~78 hand-copied headers of the standalone applicant pages; it keeps `product_logo()`, `language_switch()`, `logout_control()` and the unread badge inside it, so the template tests that look for them keep passing. `StaffSidebar` and `StaffTopbar` replace the top nav in `layouts/base.html:44-272`; the role logic (`is_inspector`, `hides_office_nav`, `root_path`) moves across unchanged.
3. **Existing macros, redrawn in place.** Keep each macro's name and arguments and change only its markup, so every importer moves at once: `forms.html` (41 importers) to `TextField` / `ChoiceTile` / `Dropzone`, `badge.html` (20) to `StatusTag`, `table.html` (17) to `DataTable`, `modal.html` (9) to `Modal`, `phase_stepper.html` (28) to `PhaseStepper`, `flash_message.html` and the flash block in `base.html:275-304` to `Banner`, `card.html: stat_card` to `StatTile`.
4. **The screens in the Figma, page by page.** Resident: sign-in, start page, dashboard, household, your situation, money coming in, document upload and its modals, emergency contacts. Staff: sign-in, your cases, case record (documents tab, decision panel), admin configuration.
5. **Everything else,** moving hand-rolled `bg-blue-600 ... rounded-md` markup onto the macros as pages are touched.

## Rules for touched templates

- No hex literals and no stock palette colours (`bg-blue-600`, `text-green-800`) in a template you touch; use a macro, a `ds-*` class or a bridged utility.
- Status colour is chosen in Python: `web/colors/labels.py`, `enum_label_color` and `APP_STATUS_DISPLAY` return tone names (`magenta`, `steel`...) instead of Tailwind class pairs. The 30 runtime class strings like `bg-{{ color }}-50` go with them.
- Headers keep the logout control visible at every width; the portal runs on shared lobby tablets. The resident header's phone menu folds everything else, never Sign out.
- The staff shell below 1100px shows the sidebar as the icon rail, and below 640px hides it behind the top bar's menu disc; the designs have no staff phone layout, this keeps the shell usable on tablets.
- Nothing clickable on a resident page below `size-tap`; the existing `min-h-[44px]` floor and its tests stay.
- Print and PDF templates (letters, voucher print, statements; WeasyPrint) and e-mail templates keep their inline styles; they are out of scope.
- Restart the app after replacing a shared component file: Jinja caches each compiled template by name, and a running server keeps serving the old macro (in the prototype run this showed as HTTP 500 on every page calling the new argument until the restart).
- The landlord portal has no screens in the Figma. It takes the landlord theme (deep violet, lilac-white ground) so a landlord never mistakes it for the applicant portal; the client's review of the landlord screens in the prototype is the design sign-off for it.
